## 閱讀筆記

- 背景：作者與許多團隊合作打造 LLM agent 後的經驗整理。主要觀察是：做得好的團隊多半用簡單、可以組合的模式，而不是複雜的框架。
- 用語：把各種做法統稱為「agentic systems」，底下再分兩種架構。Workflow：LLM 與工具照著事先寫好的程式路徑走。Agent：由 LLM 自己動態決定流程與要用哪些工具，自己掌握怎麼完成任務。
- 什麼時候用：先找最簡單的解法，需要時才增加複雜度。Agentic system 通常是拿延遲與成本去換更好的任務表現，要確定這個交換划算。任務明確、需要可預測性時用 workflow；需要彈性、要靠模型判斷時才用 agent。很多應用只要把單次 LLM 呼叫配上檢索與範例調好就夠了。
- 框架：可以加快起步，但會多一層抽象，把實際的提示與回應藏起來，讓除錯變難。建議先直接用 LLM API；用框架的話要懂底層在做什麼。
- 基本積木「augmented LLM」：一個加上檢索、工具、記憶的 LLM。模型可以自己產生搜尋查詢、挑工具、決定要記住什麼。建議針對用途調整這些擴充，並提供清楚、文件完整的介面。文中提到 Model Context Protocol 是接上第三方工具的一種方式。
- 五種 workflow 模式：
  - Prompt chaining：把任務拆成依序的多個 LLM 步驟，中間可以加程式檢查。適合能乾淨拆開的任務，用時間換準確度。例：先寫大綱、檢查大綱、再寫全文。
  - Routing：先分類輸入，再導到專門的後續處理。例：簡單問題交給小模型，困難問題交給大模型。
  - Parallelization：同時跑多個 LLM 呼叫再彙整。兩種變化：sectioning（拆成互不相干的子任務平行做）、voting（同一任務跑多次取多元結果）。
  - Orchestrator-workers：一個中央 LLM 動態拆任務、分派給 worker LLM、再整合結果。適合事先無法預測子任務的情況，例如要改很多檔案的程式修改。
  - Evaluator-optimizer：一個 LLM 產出，另一個評分並給回饋，形成迴圈。適合評估標準清楚、反覆修改確實有幫助的任務。
- Agent 怎麼運作：從人的指令或討論開始，之後自己規劃與行動，必要時回頭問人。本質上是 LLM 在迴圈中根據環境回饋使用工具。每一步都要從環境取得「ground truth」（工具結果、程式執行結果）來判斷進度。可以在檢查點或卡住時停下來等人。通常任務完成就結束，但也常設定停止條件（例如最多幾輪）來保持控制。
- 風險：自主性帶來較高成本，以及錯誤一步一步累積的可能，建議在沙盒中充分測試並搭配護欄。
- 三個核心原則：設計保持簡單；透明，把 agent 的規劃步驟明確顯示出來；仔細設計 agent 與電腦之間的介面（agent-computer interface, ACI），把工具文件寫好並測試。
- 工具設計（附錄）：對工具下的工夫應該和對提示一樣多。選模型容易寫的格式；站在模型的角度想，把工具說明寫得像給新進同事看的文件（含範例、邊界情況）；多測各種輸入再修；設計成不容易用錯（poka-yoke）。文中的例子：要求一律用絕對路徑後，相對路徑造成的錯誤就消失了。

## 值得注意

- 頁面上有註記：文中描述的許多工具之後已經改變。
- 「workflow」與「agent」的區分是這篇自己的定義，其他機構不一定這樣用詞。
- 文中沒有給出量化的成功率數字。
