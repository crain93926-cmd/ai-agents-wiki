## 閱讀筆記

- 性質：寫給產品與工程團隊的指南，內容整理自許多客戶部署的經驗，共 32 頁左右。
- 定義（第 4 頁）：agent 是能代替使用者獨立完成任務的系統。它用 LLM 來管理流程的執行與決策：判斷流程什麼時候完成、必要時修正自己的行動、失敗時把控制權交還給使用者。它也能使用工具來取得資訊與採取行動，並依照流程當下的狀態挑選工具。
- 什麼時候該做 agent（第 5 頁）：適合傳統規則式自動化處理不好的流程，分三類：（1）需要複雜判斷，例如退款核准；（2）規則多到難以維護，例如供應商安全審查；（3）大量依賴非結構化資料，例如處理房屋保險理賠。不符合這些條件的話，確定性的做法可能就夠了。
- 三個核心元件（第 7 頁）：模型（負責推理與決策）、工具（用來採取行動）、指示（定義行為與護欄）。
- 選模型的建議：先用能力最強的模型做出原型並建立評估基準，再試著在表現還能接受的地方換成較小的模型，以降低成本與延遲。
- 三種工具（第 9 頁）：資料類（取得資訊，如查資料庫、讀文件、搜尋網路）；行動類（改變系統狀態，如寄訊息、更新紀錄、把案件轉給真人）；協調類（把其他 agent 當成工具來呼叫）。
- 指示（第 11 頁）：從既有的作業流程或政策文件出發，把任務拆成小步驟，每一步對應明確的行動或輸出，並用條件分支處理邊界情況。
- 單一 agent 的執行迴圈（第 14–15 頁）：一個模型帶著工具與指示反覆執行，直到符合離開條件。離開條件包括：呼叫了代表最終輸出的工具、模型回覆時沒有再呼叫工具、發生錯誤、達到最大回合數。
- 什麼時候拆成多個 agent（第 16 頁）：提示裡的條件判斷太複雜，或工具太多太像、把工具說明寫清楚也沒用時。指南建議先把單一 agent 用到極限。
- 多 agent 的兩種模式：manager 模式（第 17–19 頁），一個中央 agent 把專門的 agent 當工具呼叫，自己保有對話的主導權並整合結果；decentralized handoff 模式（第 21–22 頁），地位對等的 agent 依專長把控制權交接給彼此，適合分流類的情境。
- 護欄（第 24–31 頁）：要多層搭配，單一護欄不夠。列出的種類：相關性分類器、安全分類器（偵測 jailbreak 與 prompt injection）、個資過濾、內容審核、工具防護（依風險高低分級，高風險動作要把關）、規則式防護（黑名單、長度限制、regex）、輸出驗證。
- 建議從資料隱私與內容安全做起，再依實際遇到的狀況增加護欄；護欄也要搭配身分驗證、存取控制等一般的軟體安全措施。
- 人類介入（第 31 頁）：兩種情況要交給真人：超過失敗門檻（例如多次無法理解使用者的意圖）；高風險動作（例如取消訂單、核准大額退款、付款），直到 agent 的可靠度被驗證為止。
- 結論（第 32 頁）：打好模型、工具、指示的基礎；從單一 agent 開始，需要時才走向多 agent；每個階段都加護欄；逐步上線並用真實使用者驗證。
